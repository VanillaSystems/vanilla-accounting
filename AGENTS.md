# Vanilla Accounting

Read [MISSION.md](MISSION.md) first: every change is judged by it. Work goes to code first, to the AI
where judgement is needed, to the person only for what only they can decide; a person's
correction is kept and learned from; whatever the AI does, a person can also do by hand.

Before adding a feature, decide where it belongs ([ADR 0015](docs/adr/0015-base-cases-in-the-app-long-tail-in-the-workspace.md)):
the app ships the common path with its empty state, its base errors and a way out by hand, plus
the invariants, security boundaries and contracts; what is specific to one company, vendor or
provider grows in that company's workspace, written by the AI with the person. Never add a
branch for one vendor or provider to the app.

Vanilla Accounting is the app; one company's books are a workspace: the folder `vanilla-accounting/`
of the company's repository (ADR 0013), opened by `VANILLA_WORKSPACE` (the repository or that
folder) or found from the cwd. Inside it: the settings (`belege.workspace.yaml`, `sources/`, …) and
`knowledge/` at the top, `ledger.json` (closedThrough and the rest of the config),
`master-data/accounts.json`, and per fiscal year `transactional-data/<year>/` (`books/*.jsonl`,
`receipts/`, `bank-statements/`, `filings/`, `invoices/`, `expected/`); the one list of these names
is `LAYOUT` in src/workspace/workspace.ts, and `npm run doctor` names every other file. The bundled
demo repositories are `demo/` and `demo-consulting/` (`VANILLA_WORKSPACE=demo`, `=demo-consulting`),
generated by `npm run demo:generate`, the only writer of the originals: `npm start` and the Mac app open a
demo as a copy outside the repository (src/workspace/demo-copy.ts; `npm run demo:reset` starts it afresh), so
nothing a person does there, a connected mailbox above all, reaches the public repository. These rules hold for any workspace. A
workspace may add its own notes in `docs/company/AGENTS.md` of its repository: read that file too when it exists.

Never write a workspace's identity (company name, UID, owner), bank ids, amounts or item
numbers of its books, or a private supplier into app files. `npm run check-public` finds them
(src/publish/leak-guard.ts); public-files.txt lists what the public app repo may contain.

# Golden rules

1. **A filed quarter is set in stone.** Once a quarter's VAT return is filed with the ESTV, that quarter and every quarter before it can never change again. Their journal entries, their figures, and their returns (`transactional-data/<year>/filings/`) stay exactly as filed. This holds for the UI, the API, CLI scripts, ad-hoc scripts and Claude alike. `config.closedThrough` marks the line. Every correction is booked in the next quarter that is still open, and declared with a Korrekturabrechnung (ESTV form 0535) of the quarter it corrects:
   - **The books were wrong:** book a correction entry (Stornobuchung or Korrekturbuchung) dated in the open quarter, with `corrects: "YYYY-Qn"` set to the quarter it corrects. Its description names the original entry id. The tag keeps it out of the open quarter's return and puts it into that quarter's 0535 (MWST tab → Korrekturabrechnung; rule: `entriesForReturn` in src/accounting/declarations.ts).
   - **The books were right, but a filed return was wrong** (e.g. a calculation bug left booked tax out): do NOT book anything again. The 0535 recomputes the quarter from today's books with today's engine, so the difference shows up there by itself. A `config.vatAdjustments` line is only for a VAT event of the open quarter that refers to a filed entry (e.g. import VAT refunded now on a filed import). Booking it again would count the tax twice in the books.
   - Never regenerate, re-export or "fix" a filed return. `npm run vat-xml` refuses filed periods.

Processes (read first for any quarter work):
- The quarter's work is defined in processes/*.flow.yaml (who does what, in which order), processes/*.guide.yaml (rules true for any company) and processes/{suppliers,customers,authorities}/<id>.yaml (facts of one business true for every company: Coop Pronto, FedEx, Shopify, the ESTV, …). The workspace's own knowledge is a second layer: knowledge/{suppliers,customers,authorities}/<id>.yaml (accounts, company rules and precedents per business, and the private ones) and knowledge/rules/<process>.guide.yaml (company rules and precedents per step). One file per business, in the folder of its main role (`roles:` lists others). See processes/README.md.
- For an item, read only the step's section in both layers (processes/<process>.guide.yaml and knowledge/rules/<process>.guide.yaml) and its own business's section in both layers — never every vendor's rules.
- Before executing a step that has `with: { guide: ... }`, read that guide section. Decide by its rules, then its precedents. If neither covers the case, take the step's new_case exit — do not guess and do not ask in chat without recording the answer.
- Every human answer goes back into the guide in the same session (new-case.flow.yaml). Run `npm run check-processes` after editing any flow or guide.

Rules the app carries out (src/booking/rules.ts, docs/0.4.0/saving.md "One click for a rule"):
- A wish about how payments are booked («buch Swisscom immer auf Telefon», «frag mich bei Barbezügen über 500 Franken») becomes a rule the app executes, never a sentence nothing acts on. Write it in the step `classify` of `knowledge/rules/booking.guide.yaml`, or, for one business, in its file under `steps: booking.guide.yaml#classify` (no `when` needed there). `then` is a map:
  ```yaml
  - id: swisscom-telefon                     # in knowledge/suppliers/swisscom.yaml
    then: { account: "6510", vat: 81 }       # book: this account; the rate only with Swiss VAT on the receipt
    source: wish 2026-10-15
  - id: barbezug-gross                       # in knowledge/rules/booking.guide.yaml
    when: { text: "Bargeldbezug|Bancomat", direction: out, amount: { over: 500 } }
    then: { ask: "Wofür war der Barbezug?", account: "2451", vat: none }   # ask first; account and vat: the proposal
    source: wish 2026-10-15
  - id: swisscom-privatanteil                # in knowledge/suppliers/swisscom.yaml
    then: { account: "6510", vat: I81, private: 50 }   # 50 % on the owner's account without VAT, the rest on 6510
    source: correction 2026-10-16
  - id: sumup-umsatz                         # in knowledge/rules/booking.guide.yaml
    when: { text: "SumUp" }
    then: { account: "3400", vat: V81, fees: { account: "6840", vat: I0 } }   # a payout: gross sales and the provider's fees apart
    source: wish 2026-10-16
  ```
  `when` takes `counterparty` (a business's file id), `payer` (the payer's IBAN or bank counterparty text: what an answered «Verkauf ohne Rechnung» question keeps), `text` (a pattern over the payment's text and the bank's counterparty name), `direction` (`in`, `out`), `amount` (`over`, `under`, in the books' currency), `account` (the bank account that paid). `vat` is a rate (`81` or `8.1`, `0`): the account gives the code, I or M or V (issue #64); a code (`I81`) is read as its rate on the account, a code no rate states (`B81-1`) as written. `vat: none` books without a VAT code. `private: <percent>` books that share on the owner's account without VAT and the rest on `account` with `vat`; the lines add up to the payment. `fees: { account, vat }` is for a card terminal's or payment provider's payout («bei SumUp immer so»): the gross sales on `account` with `vat` (a refund with its minus) and the provider's fees on `fees.account` with `fees.vat`, in the figures the model reads from the payout report linked to the payment; without a report nothing is booked: the payout waits as a question under Aufgaben («Auszahlungsbericht fehlt …», workflows/ask) with the whole payout as sales for «Übernehmen», and the question closes when the report is linked; with a report and no model the payment waits. `fees` goes with neither `private` nor `ask`. `off: true` switches a rule off. `source:` starts with `wish <date>` for a wish, `correction <date>` for a person's correction, `hand <date>` for a rule made in the form of Firma › Regeln, `notes <date>` for a rule kept from a sentence of a partner's notes, which it quotes in `note: "…"` (src/knowledge/note-rules.ts: code decides whether such a rule is offered; the notes mark the sentence «führt die App aus»).
- A payment belongs to a business (its file, and the rules in it) by the business's `match`: `uid` (on a linked receipt), `iban` (the other party's account on the statement), `domain`, `tx` (a part of the bank's counterparty name or of the merchant in its text: a bank puts the name in either field), `file`. Give a customer or supplier rule an `iban` when the statement shows one; a name in `tx` matches the counterparty field too.
- Draft a rule as narrow as the wish: a business, a payer or an amount, never a bare common word («Werbung») in `text`. A rule that rests on single words alone, or whose payments are booked today on two or more other accounts or on the owner's private account (RulePreview.spread), is kept only after the person confirms it on its card («Trotzdem behalten»), having seen the payments it matches; «Speichern» refuses it. Never change a neighbouring rule to make room for a new one: the card shows every changed rule as it was and as it would be, and the person decides.
- The person keeps a rule with «Behalten» on its card; a rule the app cannot carry out is refused there. Before that, the card shows in code what the rule would do: the payments of the open year it matches (count, the newest five, each with the booking it would make and its booking today) and the other rules that hold for the same payments (src/booking/rule-preview.ts). Firma › Regeln lists every rule with how often it booked and how often it asked; its «Neue Regel» makes one without the AI (src/saving/hand-rule.ts): drafted into its file and shown on the same card. To remove one, draft the file without it: the card asks «Ja, entfernen» and says how many of its questions are open; removing or switching off an ask rule closes its open questions, and the next run books those payments. «Übernehmen» on a question books the proposal, and replaces a booking the app made meanwhile (never a person's).
- A person's split of a payment into a business part and a private part (by hand or by a wish) offers «Immer so?» under the answer: the click drafts the rule with `private:` for that business (or payer), shown on its card (src/saving/share-rule.ts).

Special cases:

- camt053 contains transactions, where some of them are grouped. they have child transactions. A Sammelzahlung with several parts stays one transaction (tests/camt053.test.ts).
- charges to Wise credit card and be split into multiple accounts. it will first take the currency of the payment until that is exhausted, then take more money from other foreign currencies and last from the base currency account which is CHF
- companies like Aliexpress, Amazon, fedex group multiple receipts into one payment/transaction
- Cash basis taxation is used
- Wise monthly PDF bank statements show the original foreign currency amount for cross-currency charges (e.g. a USD charge deducted from the Wise EUR account shows the USD amount in the PDF). This foreign currency amount does not appear anywhere else and is the key for matching receipts denominated in that foreign currency to the correct journal entry.
- a regularly VAT taxed Swiss sales tax code is V81. If there is a refund, then its with a minus => -V81

Foreign-currency conversion:
- Book every foreign entry in CHF using the official ESTV daily SELL rate (Devisenkurs Verkauf) valid on the PAYMENT date (the underlying BankTransaction's date), per MWSTG Art. 24 on cash basis. NOT a flat annual rate. See docs/adr/0001-foreign-currency-conversion.md.
- Rates live in reference/estv-daily-rates-2026.json (refresh/extend with `npm run fetch-rates`). `classify` stamps the correct rate on new entries; `npm run restamp-fx` backfills/normalizes existing ones. Both go through src/accounting/fx-rates.ts — never re-introduce a flat per-currency rate for booking.
- reference/wechselkurse.txt (flat EUR 0.91/USD 0.78) is legacy: a last-resort fallback only, and still fine for match.ts receipt↔transaction proximity ranking.
- Consequence: the EUR/USD bank accounts need a year-end exchange-difference (Kursdifferenz) revaluation against the 31.12 rate.

Receipt collection / vendor scraping:
- Before doing any receipt-collection, email-fetch, or webshop-scraping work, read docs/runbooks/receipt-collection.md first — check the Vendor Quick Index at the top for the vendor you're handling.
- Before filing a receipt for any vendor listed in that index, verify the artifact matches what the procedure requires, not just "a PDF exists". Example: for AliExpress only the Alibaba **"Tax Invoice"** PDF (shows CHE-447.613.666 MWST + an explicit 8.1% tax amount; saved `{orderId}_payment.pdf`) is valid VAT proof, and it is only downloadable for some orders. The order-detail **"Receipt" button downloads an "Order Summary"** (`{orderId}.pdf`, API `...taxation.nonTax.receipt...`) with NO CHE number and NO tax amount — it looks official but is NOT valid proof; filing it silently loses the VAT deduction. When no Tax Invoice is available, fall back to the documented 3-page screenshot capture. Always verify a downloaded PDF actually says `Tax Invoice` + `CHE-447.613.666` before filing.
- If a vendor is NOT in the Vendor Quick Index and turns out to have a non-obvious quirk (no invoice, hidden VAT, unusual login flow, multi-order splitting, etc.), that is new procedural knowledge. STOP, tell the user what you found, and add a section (plus an index entry) to docs/runbooks/receipt-collection.md in the same session (a private supplier, or this company's mailboxes: docs/company/receipt-collection.md) — do not let a worked-out procedure live only in chat history.
- Before reporting a collection session as done, self-check: did every vendor with a documented procedure actually follow it (not just "something got downloaded")? Did every newly discovered quirk get written back to the runbook? If either answer is no, say so explicitly instead of reporting the session as clean.

VAT code rules:
- A VAT code with a rate (I81, M81, V81) may ONLY be used when the receipt explicitly shows Swiss MWST was charged. Always check the receipt — the receipt is the source of truth. Do not assume based on vendor country — foreign vendors (Amazon.de, Google, Anthropic) can be registered for Swiss MWST and charge 8.1%.
- No receipt = no VAT refund = use I0/M0/V0.
- Refunds invert the original VAT code: if the original was I81, the refund is -I81. If original was I0, refund is -I0.
- I-codes are for investment/operating expenses, M-codes for materials/goods, V-codes for sales revenue.
- Items under ~CHF 150 should be expensed (6xxx accounts), not capitalized (1xxx asset accounts).
- Bezugsteuer (MWSTG Art. 45): a SERVICE from a foreign supplier that charges no Swiss MWST (Google Ads, consultants abroad, online services) is booked B81-1 — Ziffer 383 declares 8.1%, the same entry deducts it at 405, net 0. As a VAT-registered company we owe it from the first franc; the CHF 10,000 threshold (Art. 45 Abs. 2 lit. b) only applies to recipients NOT registered. Not for goods (import VAT), not for exempt services like Stripe fees (Art. 45a). Rule: processes/booking.guide.yaml#purchase_vat pv-bezugsteuer.

Shopify billing:
- Shopify is registered for Swiss MWST and charges 8.1% on their fees (Webshop Gebühren). The per-order payout PDFs do NOT show the MWST — the proof is in Shopify's monthly billing statements (Settings → Billing → Bills in Shopify Admin). These monthly bills must be downloaded and filed as receipts to justify I81 on Webshop Gebühren entries.
- The monthly Vorsteuer on those fees is booked as a single-leg correction (empty Soll / C 6580 / M81-2), NOT a two-legged entry against 2451. See docs/runbooks/booking-patterns.md.

Kinds of firm (the VAT setup):
- `company.vat` of belege.workspace.yaml is one typed value the whole app reads (src/workspace/vat-setup.ts, parsed in src/workspace/manifest.ts, handed to the engines with the jurisdiction by `setJurisdiction`): `{ registered: false }`; `{ registered: true, method: effective, reporting: received, period: quarterly }` (what a manifest without `registered` and `period` means); or `{ registered: true, method: net-rate, reporting: received, period: half-yearly, rates: [{ rate: 4.5, label: Schreinerei, activityId: "99901" }] }` with one or two approved net tax rates (Saldosteuersatz). `vatSetup()`, `filing().length` and `vat()` in src/engines/index.ts answer every question about it; no other code checks a setup field.
- Not registered: the tax-code engine knows no code (`vat().codes.parse` is null for every code), so every entry is gross: the classifier's prompt says so and `permittedCode` (src/booking/classify.ts) drops what the model still writes, rules and invoices book without codes, the intake's VAT step and the sale questions do not run, the MWST page says the firm files no return and shows the calendar year's turnover against the threshold of modules/ch/registration.yaml. Its invoices carry no VAT (`chargesVat()`, `invoiceRates()` in src/engines/index.ts: the only rate is 0, no exemption asked, no «MWST» after the UID). The bookkeeping period stays the quarter (seals), but nothing is filed, so the year-close checklist has no «Q4 filed» and no closed quarters: the year close sets closedThrough to 31.12. and seals the whole year.
- A code the firm's form does not take (`formTakes`, src/accounting/vat-codes.ts) is refused wherever a person books: `assertCodeTaken` in src/server/edits.ts (400 `codeNotTaken`) on a new entry, a change, a payment booked by hand and the sidebar's changes; a rule's `vat` must pass it too; the UI's code lists show `firmCodes()`.
- The engines are one global per process (`setJurisdiction`). Only opening books may switch them: `workspaceAt`/`openWorkspaceAt`. To read another workspace's name or manifest while books are open (the desktop's recent list), use `readManifest`, never `workspaceAt` (r5f-18).
- Net tax rate method: the form is modules/ch/return-net-rate.yaml (form 0553; which codes it takes, its rate rows 323/333 for the firm's first and second approved rate), the codes F1/F2 of modules/ch/tax-codes.yaml `netRateCodes` whose rate is the firm's. A sale is booked gross with F1 (saleCodeOf), the tax is the rate on the gross; a purchase carries no code (no input tax); B81 is owed in 383 without the deduction; V0/V0-E stay. Returns are half-yearly: `2026-H1` is a filing key, `seal-H1.json`, `mwst-ech0217-2026-H1.xml` (eCH-0217 simpleTaxRateMethod, which names each rate by its `activityId`: setup and Firma › MWST ask for it, the review task withholds «Freigegeben» while it is missing, and the XML step refuses with `activityIdMissing`), corrections carry `corrects: "2026-H1"`. Uncertain and said so in the files: the box numbers 323/333 (from Banana's code list, the paper form was not at hand), 470/471 credits and 415 are not modelled.
- The method holds for whole years: `PATCH /api/workspace { vat }` refuses a change of registration, method, period or a rate's percent while the open year has entries (code `vatMethodHeld`); a label or an activity code changes any time. `npm run init` asks the method, basis and period only of a registered firm and the rate(s) on the net tax rate method (`--net-rate 4.5:Schreinerei`); the desktop form does the same.
- Demo workspaces of each kind: `demo-coiffeur/` (Einzelfirma, not registered) and `demo-schreinerei/` (GmbH, Saldosteuersatz 4.5 %, H1 filed), generated by `npm run demo:generate`, with golden sets under tests/golden/; tests/firm-types.test.ts holds the hand-worked figures.

VAT filing (MWST-Abrechnung):
- `npm run vat-report [-- <period> --detail]` prints the ESTV Ziffern per filing period of the current year (quarters, plus H1 as a sum, or half years); `--detail` shows the transactions behind each figure.
- `npm run vat-report-html -- <out.html>` renders a printable filing summary with per-Ziffer breakdown.
- `npm run vat-xml -- <YYYY-Qn> [out.xml]` emits (company UID and name from belege.workspace.yaml) an eCH-0217 E-MWST v2.0.0 XML for the ESTV "MWST abrechnen" import. Effective method, gross (grossOrNet=2), formOfReporting=2 (vereinnahmt/cash basis). payableTax is computed the eCH way (tax on rate-total turnover, not per-entry sum) — can differ from the UI by a Rappen; the XML is authoritative. Validates against the official XSD. Spec: docs/specs/eCH-0217-V2.0.0-E-MWST_de.pdf.
- As-filed returns are archived under `transactional-data/<year>/filings/` — never regenerate those in place; generated copies go to the workspace's `data/` (not in git).

Period close (Periodensperre):
- `config.closedThrough` in ledger.json locks all journal entries dated on or before that date. Which quarters are filed, and when, is in the workspace's notes.
- NEVER modify, delete, or add journal entries dated inside a closed period — not via the UI/API (returns 403), not via CLI scripts, and not via ad-hoc node scripts editing the books' files. This applies to Claude too.
- Opening balances (`config.openingBalances`) of the books' first year are no part of a filed quarter: they enter no VAT return and no seal covers them (seals hash entries, payments and links), so Firma › Eröffnung takes them until the year is closed through 31.12. (`openingLock`, src/accounting/opening-balance.ts). Never book a missing opening as an entry in the open period instead: it would sit in the wrong quarter of every Bilanz.
- Corrections to closed periods are booked as NEW correction entries dated in the open period (Stornobuchung/Korrekturbuchung referencing the original entry id in the description). Set `corrects: "YYYY-Qn"` on it: its VAT is declared in that quarter's Korrekturabrechnung (form 0535), which the MWST tab shows for every filed quarter (bisher eingereicht / korrigiert / Differenz), never in the open quarter's return.
- Seals: `npm run seal -- <YYYY-Qn> --close` moves `closedThrough` to a filed quarter's end and writes `transactional-data/<year>/filings/seal-<Qn>.json`, a hash of every entry, transaction and mapping dated on or before it (src/books/seal.ts). `loadBooks` checks every seal; books whose sealed part changed load read-only (`saveBooks` throws `SealBrokenError`). Never edit, delete or rewrite a seal; restore the books from git instead.
- Enforcement: every API route (src/server/routes/) that writes the index does it inside `withBooks` (src/server/books.ts: load, `update` as the person, `saveBooks`) and calls `assertOpen` first (403, proven in tests/period-lock.test.ts); `classify` skips closed-period transactions (`--force` keeps closed-period entries); `restamp-fx` skips closed-period entries. CLI and collect scripts read and write the index only through src/books/store.ts: `loadBooks`/`saveBooks` (atomic write), `periodLock(books).isClosed`, and every mutation inside the write door `update(books, actor, fn)`, which throws if a closed entry, closed transaction or mapping to a closed transaction changed, and if an actor other than a person (a module such as intake or year-close, a workflow run) changed or removed a person's entry (`origin: 'manual'`) (tests/books-store.test.ts). A command a person runs writes as `PERSON`; code that writes on its own names itself with `moduleActor(id)`. Any new code path that mutates journal entries, transactions, mappings or receipts must do the same (an API route: `withBooks`, `assertOpen` and a row in tests/period-lock.test.ts).

UI theming (src/app/):
- Colours, fonts and shadows are tokens in src/app/styles/tokens.css (the mockup's): light under `:root`, dark under `[data-theme="dark"]`, which src/app/shell/prefs.ts and index.html set on `<html>`.
- Plain CSS, one file per area (src/app/areas/<area>/<area>.css) beside the shared shell.css and detail.css, with the mockup's class names. No CSS framework, no utility classes, no inline colours.
- No hardcoded colour in a component or an area's CSS: use `var(--ink)`, `var(--muted)`, `var(--line)`, `var(--accent)` and the other tokens, and add a token (light and dark) when none fits. Exceptions: a printed document on screen (the receipt paper, the A4 invoice sheet) keeps paper colours in both themes, and an invoice layout's colour is the user's choice.
