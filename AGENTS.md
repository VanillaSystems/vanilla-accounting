# Vanilla Accounting

Read [MISSION.md](MISSION.md) first: every change is judged by it. Work goes to code first, to the AI
where judgement is needed, to the person only for what only they can decide; a person's
correction is kept and learned from; whatever the AI does, a person can also do by hand.

Before adding a feature, decide where it belongs ([ADR 0015](docs/adr/0015-base-cases-in-the-app-long-tail-in-the-workspace.md)):
the app ships the common path with its empty state, its base errors and a way out by hand, plus
the invariants, security boundaries and contracts; what is specific to one company, vendor or
provider grows in that company's workspace, written by the AI with the person. Never add a
branch for one vendor or provider to the app.

Vanilla Accounting is the app; one company's books are a workspace: the folder `vanilla-accounting/`
of the company's repository (ADR 0013), opened by `VANILLA_WORKSPACE` (the repository or that
folder) or found from the cwd. Inside it: the settings (`belege.workspace.yaml`, `sources/`, …) and
`knowledge/` at the top, `ledger.json` (closedThrough and the rest of the config),
`master-data/accounts.json`, and per fiscal year `transactional-data/<year>/` (`books/*.jsonl`,
`receipts/`, `bank-statements/`, `filings/`, `invoices/`, `expected/`); the one list of these names
is `LAYOUT` in src/workspace/workspace.ts, and `npm run doctor` names every other file. The bundled
demo repositories are `demo/` and `demo-consulting/` (`VANILLA_WORKSPACE=demo`, `=demo-consulting`),
generated by `npm run demo:generate`, the only writer of the originals: `npm start` and the Mac app open a
demo as a copy outside the repository (src/workspace/demo-copy.ts; `npm run demo:reset` starts it afresh), so
nothing a person does there, a connected mailbox above all, reaches the public repository. These rules hold for any workspace. A
workspace may add its own notes in `docs/company/AGENTS.md` of its repository: read that file too when it exists.

Never write a workspace's identity (company name, UID, owner), bank ids, amounts or item
numbers of its books, or a private supplier into app files. `npm run check-public` finds them
(src/publish/leak-guard.ts); public-files.txt lists what the public app repo may contain.

# Golden rules

1. **A filed quarter is set in stone.** Once a quarter's VAT return is filed with the ESTV, that quarter and every quarter before it can never change again. Their journal entries, their figures, and their returns (`transactional-data/<year>/filings/`) stay exactly as filed. This holds for the UI, the API, CLI scripts, ad-hoc scripts and Claude alike. `config.closedThrough` marks the line. Every correction is booked in the next quarter that is still open, and declared with a Korrekturabrechnung (ESTV form 0535) of the quarter it corrects:
   - **The books were wrong:** book a correction entry (Stornobuchung or Korrekturbuchung) dated in the open quarter, with `corrects: "YYYY-Qn"` set to the quarter it corrects. Its description names the original entry id. The tag keeps it out of the open quarter's return and puts it into that quarter's 0535 (MWST tab → Korrekturabrechnung; rule: `entriesForReturn` in src/accounting/declarations.ts).
   - **The books were right, but a filed return was wrong** (e.g. a calculation bug left booked tax out): do NOT book anything again. The 0535 recomputes the quarter from today's books with today's engine, so the difference shows up there by itself. A `config.vatAdjustments` line is only for a VAT event of the open quarter that refers to a filed entry (e.g. import VAT refunded now on a filed import). Booking it again would count the tax twice in the books.
   - Never regenerate, re-export or "fix" a filed return. `npm run vat-xml` refuses filed periods.

Rules the app carries out (src/booking/rules.ts, docs/0.4.0/saving.md "One click for a rule"):
- A wish about how payments are booked («buch Swisscom immer auf Telefon», «frag mich bei Barbezügen über 500 Franken») becomes a rule the app executes, never a sentence nothing acts on. Write it in the step `classify` of `knowledge/rules/booking.guide.yaml`, or, for one business, in its file under `steps: booking.guide.yaml#classify` (no `when` needed there). `then` is a map:
  ```yaml
  - id: swisscom-telefon                     # in knowledge/suppliers/swisscom.yaml
    then: { account: "6510", vat: 81 }       # book: this account; the rate only with Swiss VAT on the receipt
    source: wish 2026-10-15
  - id: barbezug-gross                       # in knowledge/rules/booking.guide.yaml
    when: { text: "Bargeldbezug|Bancomat", direction: out, amount: { over: 500 } }
    then: { ask: "Wofür war der Barbezug?", account: "2451", vat: none }   # ask first; account and vat: the proposal
    source: wish 2026-10-15
  - id: swisscom-privatanteil                # in knowledge/suppliers/swisscom.yaml
    then: { account: "6510", vat: I81, private: 50 }   # 50 % on the owner's account without VAT, the rest on 6510
    source: correction 2026-10-16
  - id: abo-eigenverbrauch                   # in a business's file
    then: { account: "6510", vat: 81, private: { share: 50, as: own-use } }   # all on 6510 I81, 50 % corrected as own use: 2451 / 6510 K81-B
    source: wish 2026-10-30
  ```
  `when` takes `counterparty` (a business's file id), `payer` (the payer's IBAN or bank counterparty text: what an answered «Verkauf ohne Rechnung» question keeps), `text` (a pattern over the payment's text and the bank's counterparty name), `direction` (`in`, `out`), `amount` (`over`, `under`, in the books' currency), `account` (the bank account that paid). `vat` is a rate (`81` or `8.1`, `0`): the account gives the code, I or M or V (issue #64); a code (`I81`) is read as its rate on the account, a code no rate states (`B81-1`) as written. `vat: none` books without a VAT code. `private: <percent>` books that share on the owner's account without VAT and the rest on `account` with `vat`; the lines add up to the payment. `private: { share: <percent>, as: own-use }` books the private share as own use (Eigenverbrauch, MWSTG Art. 31) instead: the whole payment on `account` with `vat`, and with it a line owner's account / `account` for the share with the year close's private-use code at the line's rate (K81-B, Ziffer 415; a refund takes it back with -K81-B), so the input tax stays whole in 405 and the correction shows in 415; the tax owed is the same as with `private: <percent>`. The correction is booked only when the payment's line claims input tax (no receipt with Swiss VAT: the zero code, nothing to correct), as a line of the payment itself, so it comes and goes with the payment's booking, once; a correction a person booked by hand on a ref of its own (same day, owner's account / `account`, that code) stands, and the rule then books none, while its preview counts it as booked so. A rule with `as: own-use` whose `vat` claims no input tax (`none`, `0`, Bezugsteuer) is refused, and so on the net tax rate method and without VAT registration (src/booking/rules.ts, `ruleBookingLines` and `handOwnUse` in src/booking/classify.ts). A payment provider's payout («bei SumUp immer so») takes no rule (`fees:` in a rule is refused since #203): it is a settlement of what the provider holds, see the next point. `tags: { projekt: alpha }` puts the firm's reporting dimensions (`dimensions` in belege.workspace.yaml, Firma › Dimensionen, #127) on every line the rule books or proposes; a dimension the firm does not declare is refused. `off: true` switches a rule off. `source:` starts with `wish <date>` for a wish, `correction <date>` for a person's correction, `hand <date>` for a rule made in the form of Firma › Regeln, `notes <date>` for a rule kept from a sentence of a partner's notes, which it quotes in `note: "…"` (src/knowledge/note-rules.ts: code decides whether such a rule is offered; the notes mark the sentence «führt die App aus»). `foreignTax: { rate: 19, account: "…" }` beside a zero code splits a sale abroad that carried a foreign VAT: the tax at that rate onto that account without a code, the net on `account` (never with `private`); the answer «Ausland mit ausländischer MWST» of the sale question books the same split and «Immer so?» keeps it so. A payment provider's payout («bei SumUp immer so») takes no rule (`fees:` in a rule is refused since #203): it is a settlement of what the provider holds, see the next point. `tags: { projekt: alpha }` puts the firm's reporting dimensions (`dimensions` in belege.workspace.yaml, Firma › Dimensionen, #127) on every line the rule books or proposes; a dimension the firm does not declare is refused. `off: true` switches a rule off. `source:` starts with `wish <date>` for a wish, `correction <date>` for a person's correction, `hand <date>` for a rule made in the form of Firma › Regeln, `notes <date>` for a rule kept from a sentence of a partner's notes, which it quotes in `note: "…"` (src/knowledge/note-rules.ts: code decides whether such a rule is offered; the notes mark the sentence «führt die App aus»).
- A payment provider (a shop platform, a card terminal) is a business whose file has a `provider:` section (src/knowledge/provider.ts, processes/README.md «A payment provider», #203); never a name in code. The company's file of it names the cut-over day `provider.since` (asked with the clearing account, the first day the report covers proposed, the open period's first day at the earliest; a day of the open period): from it on its payouts, sales, refunds and fees go over the clearing account; what is dated before it stays exactly as it was booked (a payout before it is a payment like any other), and the app never books an existing entry again to switch a provider over. Its payout from `since` on is booked by code bank / its clearing account without VAT once the company's file names `provider.clearing` and `since` (src/booking/classify.ts providerPayout); until then it waits for the person («Durchlaufkonto fehlt …», «Umstellungstag fehlt …»), never booked by a rule or the model. The clearing account must be a balance-sheet account. It needs no receipt and is no candidate for any match: no receipt set, no pair, no model match, no order link (receipt-wait `provider`). The sales come onto the clearing account from the provider's report, a CSV the drop recognises by the columns its app file names (`provider.reports.sales`, `.fees`; src/booking/sales-report.ts, src/intake/sales-report-import.ts): each order with its own code (delivered in the VAT territory the sale code at the rate its tax column shows, the normal or a reduced one the firm's form takes; abroad V0; an export whose tax column shows a foreign VAT (IOSS, for example), the net at V0 and the tax onto the company's `provider.foreignTax` without a code, held as `foreignTax` while that account is missing, never gross at V0, #206; a refund with the minus on its own day, `refundedAt`, an export's foreign tax back in the sale's share), each fee at `provider.fees`, booked in a foreign currency at the ESTV daily sell rate of its tax point (the day the provider collected the payment, the order's day on the agreed basis), each once by its ref (`SR-<provider>-<order>`, `SF-…`), as the module `sales-report` through the write door. Only the orders the provider collected are booked: with `provider.gateways` the report's `gateway` column decides (Shopify: `Payment Method` «Shopify Payments»), and the others (PayPal, bank transfer, a gift card, a test) are counted in the row, never booked onto the clearing account. An order of a filed period is not booked (its refund paid in the open period is). The report reaches back to `since` less the payout days (`payoutDays`, the company's may override the app's): a row of those days is booked by its own tax point when open, since its payout after `since` settles the clearing account, unless the clearing account carries it already (the old way per order, by ref or day and amount) or a payout of the provider dated before `since` and after the row's day is not booked bank / clearing account (as sales, or not yet): then it waits (legacy); a row dated earlier is counted, never booked; a domestic order without tax or at no rate the firm books, Swiss VAT on an export, and a refund without a day of its own wait for the person. One source of sales per provider: a provider with `reports.sales` takes none from a payout report; a read payout report of a card terminal books its sales and fees onto the clearing account only on or after `since` and with its payout (linked, or the one payout of what it paid out within the payout days) booked bank / clearing account already (bookPayoutReports). A missing clearing account (with the cut-over day), revenue or fee account is asked once in the drop row, with an account proposed (modules/ch/setup.yaml answers.payouts; the clearing account named after the provider and added to the chart when the answer is kept), and kept in the company's file. What the books carry from elsewhere holds what it may be (ReportContext.legacy): a sale on the clearing account no report booked holds the order its ref or day and amount name, and one on or after `since` that names none, like a payout of the provider on or after `since` booked otherwise than from the clearing account, holds every order, refund and fee up to its day; held rows wait for the person, named in the drop row and kept on the report's receipt (`report.held`, shown on its detail). «Rückgängig» takes only the report's own entries and links, refused when a person changed one, and leaves the sales another report names too. Order documents go with their sale (linkOrdersToSales, also a page known only by `orderPage`), never with the payout. An order page of a provider with `reports.sales`, dated on or after `since`, has no payment of its own (src/booking/order-pages.ts, derived on every read, #253): it waits for the order export, never for a payment, is paired with none (`noPayment` in the chain, the receipt sets and the model match) and is not in «Braucht dich»; one whose order the export reached past without booking or holding it is a receipt like any other. The quarter's review shows each clearing account's balance, its month ends and what the provider paid out after the end within its payout days, which holds sales after the end too and so is the most the balance may be, and names a balance above it or below zero as a difference (clearingCheck); a foreign-currency clearing account carries exchange differences until the year end revalues it: a fact, never a reminder.
- A payment belongs to a business (its file, and the rules in it) by the business's `match`: `uid` (on a linked receipt), `iban` (the other party's account on the statement), `domain`, `tx` (a part of the bank's counterparty name or of the merchant in its text: a bank puts the name in either field), `file`. Give a customer or supplier rule an `iban` when the statement shows one; a name in `tx` matches the counterparty field too.
- Draft a rule as narrow as the wish: a business, a payer or an amount, never a bare common word («Werbung») in `text`. A rule that rests on single words alone, or whose payments are booked today on two or more other accounts or on the owner's private account (RulePreview.spread), is kept only after the person confirms it on its card («Trotzdem behalten»), having seen the payments it matches; «Speichern» refuses it. Never change a neighbouring rule to make room for a new one: the card shows every changed rule as it was and as it would be, and the person decides.
- The person keeps a rule with «Behalten» on its card; a rule the app cannot carry out is refused there. Keeping it books the open payments without a booking it decides at once (the booking run per payment, src/server/routes/rules.ts `bookKept`; runs still going are named and close their tasks when they rest; the server records each keep beside the runs, src/workflows/keeps.ts; its result line and its «Rückgängig» `POST /api/rules/kept/undo { keep }` name only the keep's id, refused while a later keep of the same file stands, never a person's booking) and closes their tasks; one that waits for its receipt is shown waiting on the card (`PreviewPayment.waits`, `RulePreview.open`), never as a booking the keep makes (#383). Before that, the card shows in code what the rule would do: the payments of the open year it matches (count, the newest five, each with the booking it would make and its booking today) and the other rules that hold for the same payments (src/booking/rule-preview.ts). Firma › Regeln lists every rule with how often it booked and how often it asked; its «Neue Regel» makes one without the AI (src/saving/hand-rule.ts): drafted into its file and shown on the same card. To remove one, draft the file without it: the card asks «Ja, entfernen» and says how many of its questions are open; removing or switching off an ask rule closes its open questions, and the next run books those payments. «Übernehmen» on a question books the proposal, and replaces a booking the app made meanwhile (never a person's).
- A payment out that needs a receipt is not booked while none is linked (issue #29, src/booking/receipt-wait.ts): no provisional booking; it is marked `waitsForReceipt` and booked once a receipt is linked, by a rule or the model alike. Booked or asked at once: money in, the bank's fee row (one the bank itself coded as its charge, ACMT or PMNT with CHRG or FEES, read again from its statement file since the books keep no bank code, is booked by code before any model is asked, bank / the jurisdiction's bank-charges account of modules/ch/setup.yaml `bankCharges` without a VAT code, a refund the other way, unless a company rule matches it; a `bank-fee` row only by the bank's name as creditor (a loan, interest) or a custody fee goes to the model or the person; a chart without that account as an expense account leaves it to them too, the form naming the account; src/booking/bank-fee.ts, #359; the fee of another payment, Wise's, stays with the model), an own transfer, a booking onto the owner's account, a money account or a debt (settlementAccount; the model's answer decides it once for a payment without a rule, the owner's account only for a payment to the owner, her name in its counterparty or text: a supplier's payment the model puts there waits, issue #201, answerSettles), a rule that asks first, `noReceiptNeeded`, a firm without input tax, a business whose file has `apply: { receipt: none }` on a rule of `evidence.guide.yaml#rules`, and a wage on a firm whose setup says it has staff or an employed owner (`profile.employees`, issue #340): by the payment's own text, never the counterparty's name (`ev-exempt-wages` there, `apply: { receipt: none, firm: employer, text, not }`), and freed from the wait only, so a receipt that matches it is still paired and books it again (no-wait reason `wage`, never in NONE_OF_ITS_OWN). The bank's fee row is one by its code for charges or the bank's whole name, never a part of the name and never under a card payment's code. «Braucht keinen Beleg» on an unbooked payment goes on to book it in the same click (the booking run) and says what came of it. Two weeks before the return is due it becomes a task with «Beleg zuordnen», «Mit anderem Nachweis» and «Ohne Vorsteuer buchen» (src/accounting/receipt-due.ts). A payment whose only receipt cannot be read (isUnreadable) is never booked on a guessed rate: it waits for the person at once (issue #57), unless the company's file for the business has `apply: { unreadReceipt: <rate> }`; no shipped file may assume a rate.
- A person's split of a payment into a business part and a private part (by hand or by a wish) offers «Immer so?» under the answer: the click drafts the rule with `private:` for that business (or payer), shown on its card (src/saving/share-rule.ts). A payment booked whole with input tax and corrected as own use (by a line of its own or by hand on a ref of its own) offers the rule with `private: { share, as: own-use }`, also from the correction's ref. «Neue Regel» of Firma › Regeln takes a private share and, on a firm with input tax, «als Eigenverbrauch».
- A person's change of the account or code of a booking no rule made offers «Ins Wissen übernehmen?» under the entry (src/saving/learn-rule.ts): «Vorschlag der KI» asks Haiku for a rule for the business or payer, a note sentence, or nothing; code refuses a rule unless it books that payment as the person did and at least two of the partner's payments are booked so, and only then drafts it for the card. «Selbst schreiben» opens the form of Firma › Regeln.

Special cases:

- camt053 contains transactions, where some of them are grouped. they have child transactions. A Sammelzahlung with several parts stays one transaction (tests/camt053.test.ts).
- charges to Wise credit card and be split into multiple accounts. it will first take the currency of the payment until that is exhausted, then take more money from other foreign currencies and last from the base currency account which is CHF
- companies like Aliexpress, Amazon, fedex group multiple receipts into one payment/transaction
- Cash basis taxation (vereinnahmt) is what the demos use; a firm may report on the agreed basis (vereinbart, the law's default), see «Kinds of firm»
- Wise monthly PDF bank statements show the original foreign currency amount for cross-currency charges (e.g. a USD charge deducted from the Wise EUR account shows the USD amount in the PDF). This foreign currency amount does not appear anywhere else and is the key for matching receipts denominated in that foreign currency to the correct journal entry.
- a regularly VAT taxed Swiss sales tax code is V81. If there is a refund, then its with a minus => -V81

Foreign-currency conversion:
- Book every foreign entry in CHF using the official ESTV daily SELL rate (Devisenkurs Verkauf) valid on the PAYMENT date (the underlying BankTransaction's date), per MWSTG Art. 24 on cash basis. NOT a flat annual rate. See docs/adr/0001-foreign-currency-conversion.md. On the agreed basis the rate is the one of the tax point (MWSTV Art. 45 Abs. 1): an entry's own date, which is its document's for a line on an open item (`rateDateOf`, src/accounting/fx-conversion.ts).
- Rates live in reference/estv-daily-rates-2026.json (refresh/extend with `npm run fetch-rates`). `classify` stamps the correct rate on new entries; `npm run restamp-fx` backfills/normalizes existing ones. Both go through src/accounting/fx-rates.ts — never re-introduce a flat per-currency rate for booking.
- reference/wechselkurse.txt (flat EUR 0.91/USD 0.78) is legacy: a last-resort fallback only, and still fine for match.ts receipt↔transaction proximity ranking.
- Consequence: the EUR/USD bank accounts need a year-end exchange-difference (Kursdifferenz) revaluation against the 31.12 rate.

Receipt collection / vendor scraping:
- Before doing any receipt-collection, email-fetch, or webshop-scraping work, read docs/runbooks/receipt-collection.md first — check the Vendor Quick Index at the top for the vendor you're handling.

STOP, tell the user what you found, and add a section (plus an index entry) to docs/runbooks/receipt-collection.md in the same session (a private supplier, or this company's mailboxes: docs/company/receipt-collection.md) — do not let a worked-out procedure live only in chat history.

VAT code rules:
- A VAT code with a rate (I81, M81, V81) may ONLY be used when the receipt explicitly shows Swiss MWST was charged. Always check the receipt — the receipt is the source of truth. Do not assume based on vendor country — foreign vendors (Amazon.de, Google, Anthropic) can be registered for Swiss MWST and charge 8.1%.
- No receipt = no input tax for the app's own runs and for the AI: they book I0/M0 (V0 on a sale) when no linked receipt shows Swiss MWST. Only a person may deduct on other proof (MWSTG Art. 81 Abs. 3, ESTV MWST-Info 09 Ziff. 1.6: several documents that together prove the tax was charged and paid, such as a contract with the VAT and the payment confirmation; a card debit note is no invoice): she books the payment by hand with the rate and names the proof, which the payment keeps as `inputTaxProof` (issue #134). Never set it for a person.
- Refunds invert the original VAT code: if the original was I81, the refund is -I81. If original was I0, refund is -I0.
- I-codes are for investment/operating expenses, M-codes for materials/goods, V-codes for sales revenue.
- Items under ~CHF 150 should be expensed (6xxx accounts), not capitalized (1xxx asset accounts).
- Bezugsteuer (MWSTG Art. 45): a SERVICE from a foreign supplier that charges no Swiss MWST (Google Ads, consultants abroad, online services) is booked B81-1 — Ziffer 383 declares 8.1%, the same entry deducts it at 405, net 0. As a VAT-registered company we owe it from the first franc; the CHF 10,000 threshold (Art. 45 Abs. 2 lit. b) only applies to recipients NOT registered. Not for goods (import VAT), not for exempt services like Stripe fees (Art. 45a). Rule: processes/booking.guide.yaml#purchase_vat pv-bezugsteuer.

Shopify billing:
- Shopify is registered for Swiss MWST and charges 8.1% on their fees (Webshop Gebühren). The per-order payout PDFs do NOT show the MWST — the proof is in Shopify's monthly billing statements (Settings → Billing → Bills in Shopify Admin). These monthly bills must be downloaded and filed as receipts to justify I81 on Webshop Gebühren entries.
- The monthly Vorsteuer on those fees is booked as a single-leg correction (empty Soll / C 6580 / M81-2), NOT a two-legged entry against 2451. See docs/runbooks/booking-patterns.md. Code books it: a provider's document with `proves: vat-correction` (Shopify's Payments Invoice) books the VAT it shows once per bill, on `provider.fees.account` with `provider.fees.billVat` (absent: the code the account takes), in an open period only, and links the bill (src/booking/vat-corrections.ts bookVatCorrections, the booking step). A bill a person took apart from its booking (deleted or unlinked) is never booked again.

Running tests:
- While you work, run only the test files your change touches: `node --import tsx --test tests/foo.test.ts`.
- Run the full suite (`npm test`) only before you commit or merge. Never start several full suites in parallel: `npm test` takes a machine-wide lock and waits («waiting for another test run (pid N)…») while another run holds it. It runs 3 test files at once at nice 10; `TEST_CONCURRENCY=<n>` overrides the 3. A run stops after 20 minutes (`TEST_TIME_LIMIT=<seconds>` overrides it), with every process it started, frees the lock and says so (exit 124).
- The pre-push hook (tools/hooks/pre-push) runs `check-public` and then the layers lint (`node --import tsx --test tests/layers.test.ts`, about a second), so a Swiss-specific name (MWST, camt.053) outside modules/ch and src/providers, comments included, is refused before the merge gate sees it.
- A browser test starts and closes Chrome through tests/support/browser.ts (`launchChrome`, `closeChrome`), which bound both: a test file's process lives as long as its Chrome, so an unbounded start or close keeps a failed run alive.
- Its `browserPath` is the browser of every browser test: CHROME_PATH, else the newest Chrome for Testing in Playwright's cache (`npx playwright install chromium`; `PLAYWRIGHT_BROWSERS_PATH` is honoured), else an installed Chromium browser. It sets CHROME_PATH to it, so the app's code under test starts the same one. Kinds of firm (the VAT setup):
- `company.vat` of belege.workspace.yaml is one typed value the whole app reads (src/workspace/vat-setup.ts, parsed in src/workspace/manifest.ts, handed to the engines with the jurisdiction by `setJurisdiction`): `{ registered: false }`; `{ registered: true, method: effective, reporting: received, period: quarterly }` (what a manifest without `registered` and `period` means); or `{ registered: true, method: net-rate, reporting: received, period: half-yearly, rates: [{ rate: 4.5, label: Schreinerei, activityId: "99901" }] }` with one or two approved net tax rates (Saldosteuersatz). `reporting` is `received` (cash basis) or `agreed` on either method. `vatSetup()`, `agreedBasis()`, `filingBasis()`, `filing().length` and `vat()` in src/engines/index.ts answer every question about it; no other code checks a setup field.
- Agreed basis (vereinbartes Entgelt, MWSTG Art. 39 Abs. 1, Art. 40 Abs. 1): the return still declares entries by their date (`entriesForReturn`); the basis decides which entries exist. An invoice the app issues is booked on its date against the receivable with its sale codes, a credit note and a cancellation on theirs (src/invoices/events.ts, refs `RE-<number>`, `GS-<number>`, `RE-<number>-storno`, booked once on issue, cancel, a confirmed payment and every statement import); its payment only settles the receivable (`hasEvent`, decided by the books, not by today's basis, so a switch back never taxes it twice, MWSTV Art. 106); a payment dated before its invoice is a prepayment, taxed on its own date with the sale codes, and the event is rebooked for the rest (`prepaidEvent`, src/invoices/payments.ts, Art. 40 Abs. 1 lit. c). A payment's line with a sale or purchase code whose linked receipt is dated otherwise is dated by the receipt and booked on 1100/2000, and the payment settles that account on its own date, the exchange difference to 6960 (`atTaxPoint`, src/accounting/tax-point.ts, called by the classifier wherever it books or proposes); a receipt of a filed period, of the open year or of a closed earlier year the firm reported on this basis, leaves the line on the payment's date with `corrects` (an app invoice's missing event likewise); one before the books or before `company.vat.reportingSince` (the year the basis began, written by Firma › MWST on a switch; absent: before the books) leaves it as it is, an open item of the switch (`lockedTaxPoint`, MWSTV Art. 106 Abs. 1). The open-item accounts are year-end.yaml's `receivables` and `payables`. The XML writes `formOfReporting` 1. The year close proposes no Debitor whose event is booked.
- Not registered: the tax-code engine knows no code (`vat().codes.parse` is null for every code), so every entry is gross: the classifier's prompt says so and `permittedCode` (src/booking/classify.ts) drops what the model still writes, rules and invoices book without codes, the intake's VAT step and the sale questions do not run, the MWST page says the firm files no return and shows the calendar year's turnover against the threshold of modules/ch/registration.yaml. Its invoices carry no VAT (`chargesVat()`, `invoiceRates()` in src/engines/index.ts: the only rate is 0, no exemption asked, no «MWST» after the UID). The bookkeeping period stays the quarter (seals), but nothing is filed, so the year-close checklist has no «Q4 filed» and no closed quarters: the year close sets closedThrough to 31.12. and seals the whole year.
- A code the firm's form does not take (`formTakes`, src/accounting/vat-codes.ts) is refused wherever a person books: `assertCodeTaken` in src/server/edits.ts (400 `codeNotTaken`) on a new entry, a change, a payment booked by hand and the sidebar's changes; a rule's `vat` must pass it too; the UI's code lists show `firmCodes()`.
- The engines are one global per process (`setJurisdiction`). Only opening books may switch them: `workspaceAt`/`openWorkspaceAt`. To read another workspace's name or manifest while books are open (the desktop's recent list), use `readManifest`, never `workspaceAt` (r5f-18).
- Net tax rate method: the form is modules/ch/return-net-rate.yaml (form 0553; which codes it takes, its rate rows 323/333 for the firm's first and second approved rate), the codes F1/F2 of modules/ch/tax-codes.yaml `netRateCodes` whose rate is the firm's. A sale is booked gross with F1 (saleCodeOf), the tax is the rate on the gross; a purchase carries no code (no input tax); B81 is owed in 383 without the deduction; V0/V0-E stay. Returns are half-yearly: `2026-H1` is a filing key, `seal-H1.json`, `mwst-ech0217-2026-H1.xml` (eCH-0217 simpleTaxRateMethod, which names each rate by its `activityId`: setup and Firma › MWST ask for it, the review task withholds «Freigegeben» while it is missing, and the XML step refuses with `activityIdMissing`), corrections carry `corrects: "2026-H1"`. Uncertain and said so in the files: the box numbers 323/333 (from Banana's code list, the paper form was not at hand), 470/471 credits and 415 are not modelled.
- The method holds for whole years: `PATCH /api/workspace { vat }` refuses a change of registration, method, basis, period or a rate's percent while the open year has entries (code `vatMethodHeld`); a label or an activity code changes any time. `npm run init` asks the method, basis and period only of a registered firm and the rate(s) on the net tax rate method (`--net-rate 4.5:Schreinerei`); the desktop form does the same.
- Demo workspaces of each kind: `demo-coiffeur/` (Einzelfirma, not registered) and `demo-schreinerei/` (GmbH, Saldosteuersatz 4.5 %, H1 filed), generated by `npm run demo:generate`, with golden sets under tests/golden/; tests/firm-types.test.ts holds the hand-worked figures.

VAT filing (MWST-Abrechnung):
- `npm run vat-report [-- <period> --detail]` prints the ESTV Ziffern per filing period of the current year (quarters, plus H1 as a sum, or half years); `--detail` shows the transactions behind each figure.
- `npm run vat-report-html -- <out.html>` renders a printable filing summary with per-Ziffer breakdown.
- `npm run vat-xml -- <YYYY-Qn> [out.xml]` emits (company UID and name from belege.workspace.yaml) an eCH-0217 E-MWST v2.0.0 XML for the ESTV "MWST abrechnen" import. Effective method, gross (grossOrNet=2), formOfReporting=2 (vereinnahmt/cash basis). payableTax is computed the eCH way (tax on rate-total turnover, not per-entry sum) — can differ from the UI by a Rappen; the XML is authoritative. Validates against the official XSD. Spec: docs/specs/eCH-0217-V2.0.0-E-MWST_de.pdf.
- As-filed returns are archived under `transactional-data/<year>/filings/` — never regenerate those in place; generated copies go to the workspace's `data/` (not in git).

Period close (Periodensperre):
- `config.closedThrough` in ledger.json locks all journal entries dated on or before that date. Which quarters are filed, and when, is in the workspace's notes.
- NEVER modify, delete, or add journal entries dated inside a closed period — not via the UI/API (returns 403), not via CLI scripts, and not via ad-hoc node scripts editing the books' files. This applies to Claude too.
- Opening balances (`config.openingBalances`) of the books' first year are no part of a filed quarter: they enter no VAT return and no seal covers them (seals hash entries, payments and links), so Firma › Eröffnung takes them until the year is closed through 31.12. (`openingLock`, src/accounting/opening-balance.ts). Never book a missing opening as an entry in the open period instead: it would sit in the wrong quarter of every Bilanz.
- Corrections to closed periods are booked as NEW correction entries dated in the open period (Stornobuchung/Korrekturbuchung referencing the original entry id in the description). Set `corrects: "YYYY-Qn"` on it: its VAT is declared in that quarter's Korrekturabrechnung (form 0535), which the MWST tab shows for every filed quarter (bisher eingereicht / korrigiert / Differenz), never in the open quarter's return.
- Seals: `npm run seal -- <YYYY-Qn> --close` moves `closedThrough` to a filed quarter's end and writes `transactional-data/<year>/filings/seal-<Qn>.json`, a hash of every entry, transaction and mapping dated on or before it (src/books/seal.ts). `loadBooks` checks every seal; books whose sealed part changed load read-only (`saveBooks` throws `SealBrokenError`). Never edit, delete or rewrite a seal; restore the books from git instead.
- Enforcement: every API route (src/server/routes/) that writes the index does it inside `withBooks` (src/server/books.ts: load, `update` as the person, `saveBooks`) and calls `assertOpen` first (403, proven in tests/period-lock.test.ts); `classify` skips closed-period transactions (`--force` keeps closed-period entries); `restamp-fx` skips closed-period entries. CLI and collect scripts read and write the index only through src/books/store.ts: `loadBooks`/`saveBooks` (atomic write; a save over files another process wrote since the load throws `StaleBooksError` and writes nothing, issue #123: load again and redo the change), `periodLock(books).isClosed`, and every mutation inside the write door `update(books, actor, fn)`, which throws if a closed entry, closed transaction or mapping to a closed transaction changed, and if an actor other than a person (a module such as intake or year-close, a workflow run) changed or removed a person's entry (`origin: 'manual'`) (tests/books-store.test.ts). A command a person runs writes as `PERSON`; code that writes on its own names itself with `moduleActor(id)`. Any new code path that mutates journal entries, transactions, mappings or receipts must do the same (an API route: `withBooks`, `assertOpen` and a row in tests/period-lock.test.ts).

UI theming (src/app/):
- Colours, fonts and shadows are tokens in src/app/styles/tokens.css (the mockup's): light under `:root`, dark under `[data-theme="dark"]`, which src/app/shell/prefs.ts and index.html set on `<html>`.
